# Database Schema (PostgreSQL)

Schema for the Task Management API after the move from MongoDB to PostgreSQL (Task 9). The tables were first created by hand in `psql` to learn SQL. Day 29 turns them into versioned migrations.

## Relationship

```
users (1) ────< (many) tasks
  id  <──────────  user_id
```

One user owns many tasks. A task belongs to exactly one user. A user can have zero tasks.

## Table: users

| Column        | Type        | Constraints                                | Purpose                                      |
| ------------- | ----------- | ------------------------------------------ | -------------------------------------------- |
| id            | UUID        | PRIMARY KEY, DEFAULT gen_random_uuid()     | Unique identifier, generated by the database |
| username      | TEXT        | NOT NULL, UNIQUE                           | Login name                                   |
| password_hash | TEXT        | NOT NULL                                   | bcrypt hash, never the plain password        |
| role          | TEXT        | NOT NULL, CHECK (role IN ('admin','user')) | Used for role-based access                   |
| created_at    | TIMESTAMPTZ | NOT NULL, DEFAULT now()                    | When the account was created                 |

## Table: tasks

| Column          | Type        | Constraints                                                                                  | Purpose                                           |
| --------------- | ----------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| id              | UUID        | PRIMARY KEY, DEFAULT gen_random_uuid()                                                       | Unique identifier                                 |
| user_id         | UUID        | NOT NULL, REFERENCES users(id) ON DELETE CASCADE                                             | The owner of the task                             |
| title           | TEXT        | NOT NULL                                                                                     | Task title                                        |
| description     | TEXT        | NOT NULL, DEFAULT ''                                                                         | Optional details; an empty string instead of NULL |
| due_date        | TIMESTAMPTZ | NOT NULL                                                                                     | When the task is due                              |
| status          | TEXT        | NOT NULL, CHECK (status IN ('pending','in_progress','done'))                                 | Progress of the task                              |
| reminder_status | TEXT        | NOT NULL, DEFAULT 'pending', CHECK (reminder_status IN ('pending','queued','sent','failed')) | State of the background reminder from Task 8      |
| created_at      | TIMESTAMPTZ | NOT NULL, DEFAULT now()                                                                      | When the task was created                         |
| updated_at      | TIMESTAMPTZ | NOT NULL, DEFAULT now()                                                                      | When the task was last changed                    |

## Why each constraint exists

- **PRIMARY KEY on id**: every row needs a unique, stable identity. UUIDs generated by `gen_random_uuid()` can be created without asking the application, and they match the string IDs in the domain layer, so both Mongo and Postgres can be used.
- **UNIQUE on username**: two users must never share a login. The database enforces it even if two requests arrive at the same moment, which an application-level check cannot guarantee. A violation raises SQL state `23505`, which the API maps to 409.
- **NOT NULL**: columns the application cannot work without (hash, role, title, due date, status) can never be stored empty by mistake.
- **CHECK on role, status and reminder_status**: only the allowed values can be stored. A bad value raises SQL state `23514`. This protects the data even if a bug or a manual query tries to write something invalid.
- **FOREIGN KEY tasks.user_id → users.id**: a task cannot exist without a real owner, so there are no orphaned tasks.
- **ON DELETE CASCADE**: deleting a user also deletes their tasks, so nothing is left behind.
- **TIMESTAMPTZ**: times are stored in UTC and shown in the client's time zone, which avoids off-by-hours bugs in due-date and reminder logic.
- **DEFAULT values**: `reminder_status = 'pending'` means a new task is automatically eligible for a reminder, and `created_at` / `updated_at` are filled in by the database.

## Indexes

None yet. Besides the primary keys and the unique index on `username` (both created automatically), indexes are added on Day 29:

- `idx_tasks_user_due` on `tasks (user_id, due_date)` for the per-user list query
- `idx_tasks_reminder_pending` on `tasks (due_date) WHERE reminder_status = 'pending'` for the reminder scheduler

## Test data used for practice

3 users (alice: admin, bob: user, carol: user) and 10 tasks. Alice has 4, bob has 6 and carol has 0, so queries with a LEFT JOIN can be checked against a user with no tasks.

## Query: number of tasks per user

```sql
SELECT u.username, COUNT(t.id) AS task_count
FROM users u
LEFT JOIN tasks t ON t.user_id = u.id
GROUP BY u.id, u.username
ORDER BY task_count DESC;
```

`LEFT JOIN` keeps users who have no tasks (task_count = 0). A plain `JOIN` would drop them. `COUNT(t.id)` counts only real task rows, whereas `COUNT(*)` would count 1 for a user with no tasks.
